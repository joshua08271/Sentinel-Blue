# Automatic service recovery

Version 1.9.32 additionally supports [coordinated autonomous repair](AUTONOMOUS_REPAIR.md): explicitly authorized configuration restoration and service recovery in one verified transaction, plus local unhealthy-application restarts. The following describes the original `restart_service` path, which remains available for profiles without the new `repair_service` policy.

Version 1.9.16 adds `controller --auto-recover-services`. Keep the controller's existing TLS, identity, event profile, and recovery arguments when adding this flag. It is disabled by default and startup refuses it unless the event profile authorizes automatic `restart_service` actions in guarded or range autonomy.

For each service to recover automatically:

- Confirm its manifest and set `host` to the exact agent identifier and `service_id` to the native service name.
- Include `restart_service` in the manifest's `allowed_automatic_actions` and the profile's global automatic actions.
- Declare the exact application checks in `expected_transactions`. Configure these probes on the agent, including dependency checks.
- Declare service definitions, startup scripts, and critical configuration in `required_files`, and configure their integrity collection. Every required file must be present and unchanged in an approved baseline. Native file preflight uses the restoration reader's 2 MiB per-file limit.
- Declare required accounts and dependencies. Dependencies refer to unique service manifests on the same host. Missing, ambiguous, cross-host, or cyclic dependencies hold recovery. The planner recovers an eligible stopped dependency first and waits for later healthy observations before starting a dependent service.
- In version 1.9.17 and later, enable `agent --allow-service-recovery` (or inventory `allow_service_recovery: true`). This requires the profile’s `in_place_repair` capability. Session containment has its own independent flag; enabling it alone no longer enables service recovery through the CLI.

The controller requires two consecutive sequenced observations from the same boot and approved baseline, within 90 seconds of collection. A healthy service, incomplete collection, a changed baseline, a sequence gap, changed required files, a disabled required account, or an unavailable dependency resets confirmation. Restarting the controller also resets confirmation.

Immediately before execution the agent independently checks the manifest contract, telemetry freshness, current native dependency states, dependency application checks, and required file bytes throughout the declared dependency chain. Windows required files also need matching approved security descriptor hashes. Files listed only under `required_data` are not treated as immutable configuration; their application semantics must be covered by the declared transactions.

Linux native `inactive` and `failed` states are recognized as stopped; Windows disabled startup modes are compared without case sensitivity. An unknown, absent, masked, or transitioning native service is held for review. An already running service receives validation without a start or stop command. Recovery starts an explicitly stopped service and requires three consecutive healthy probe rounds during a bounded startup grace. A failed validation restores the prior service state. Interrupted transactions with uncertain outcomes remain held for review.

Both controller action history and agent transaction history enforce recovery limits: a five-minute cooldown and at most three start attempts per service per hour. Controller limits count queued attempts, including failed or undelivered ones. Unknown outcomes block repeats. These limits survive process restarts and prevent an outage from causing an unlimited restart loop. Successful automatic recovery closes its alert so a later outage can form a new episode.

Controller dashboard data exposes `automatic_service_recovery`, `service_recovery_confirmations`, and `service_recovery_status`. Version 1.9.24's recovery panel combines current observations, telemetry freshness, governance, agent availability, and the durable admission budget. Each row includes the observation status and a `budget` with `allowed`, `reason`, `attempts_in_window`, and `retry_at`. A retry time is only the earliest budget opening; fresh observations and every other gate still apply. Unresolved outcomes have no automatic retry time. Execution holds and attempt limits are recorded in action results and policy audit events.

These checks cover declared dependencies, accounts, files, and transactions. They cannot discover every necessary configuration file or validate an application that has no meaningful health transaction. They do not install arbitrary missing applications, repair a compromised kernel, or prove a root-controlled host trustworthy. Use an external trusted recovery path when host trust is lost.

Ordinary controller SIGTERM/SIGINT shutdowns drain active requests and finish the authenticated controller session. A crash or forced kill still preserves the dirty marker and resumes in safe governance for explicit operator review. Discovered Linux systemd aliases are monitored through their canonical files while alias paths remain in persistence telemetry; changed destinations require fresh manifest/baseline review. Explicit protected paths are never silently redirected.

Version 1.9.18 schedules Windows session inventory after the other bounded native collectors and excludes only the querying PowerShell process itself. Other sessions retain exact process-identity checks. Controller-local relay observations never obtain remote-agent authority; their intentionally unbound metadata does not trigger a global storage quarantine. Invalid external agent metadata remains quarantined.

Version 1.9.19 polls queued actions before collecting and before publishing a healthy replacement sample. Actions use the last accepted observation; native action preflight remains required. If work arrives during collection, the agent recollects before publishing. The controller still rejects a capture whose approved observation was replaced; this guard is not relaxed. Windows full firewall inventory retains all rule/filter fields and uses a 60-second timeout with concise error reporting.

Version 1.9.20 runs at most one native inventory helper per available CPU, capped at two. This avoids competing PowerShell helpers on a single-core host. All Windows inventory queries default to a bounded 60-second timeout; explicitly shorter deadlines remain supported. Process ownership is collected in one bulk query and joined only when both PID and creation time match, avoiding per-process CIM calls and reused-PID misattribution. Missing owner matches stay unknown. Full collector coverage and the complete/fresh-observation recovery gates remain required; the change does not convert a timeout into healthy telemetry.

Version 1.9.21 timestamps telemetry before collection begins. Collection, file reads, and probe time therefore consume the existing 90-second freshness budget. A long collection cannot make earlier evidence fresh by stamping its completion time. This may hold recovery more often on an overloaded host; optimize or provision the host rather than extending evidence trust.

PowerShell inventory starts with terminating error behavior and rejects error-stream output even if the helper returns exit code zero. Malformed JSON rows and empty required account/service inventories report collection errors. Administrator group lookup failures are no longer silently treated as an empty membership list. Explicit handling of optional or transient queries remains collector-specific, so this does not prove every inventory source is complete.

The generated Windows task uses priority 4, which maps to normal process/thread priority, and short-lived collector subprocesses explicitly request normal process priority. Existing tasks need the reviewed deployment update before their parent task priority changes. The finite collector deadlines, helper concurrency cap, freshness gates, and recovery attempt limits still apply. See [Microsoft's task priority mapping](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-priority) and [Python's subprocess flags](https://docs.python.org/3/library/subprocess.html#subprocess.NORMAL_PRIORITY_CLASS). Native validation of this candidate under sustained load is pending.

The 1.9.21 native pressure comparison exceeded a 120-second collection deadline. An experimental increase in helper priority also failed to complete the inventory, so it was not adopted. The release continues to use normal priority.

Version 1.9.22 shares one PowerShell host across all three network inventory queries. The batch keeps each section and its error status separate; a failed or malformed section cannot count as a complete observation. A batch timeout remains a collection failure, without extra retry processes. Services, process identity, and boot identity query only the CIM properties they actually consume, while retaining every field used by the existing checks. [Microsoft documents property selection](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/get-ciminstance?view=powershell-7.5#-property) as a way to reduce returned object size.

The native 1.9.22 round recovered the declared Linux dependency chain and Windows IIS, restored their protected health files, and preserved the recovery cooldown after an agent restart. Sustained Windows CPU load still exceeded a 120-second inventory deadline. A clean controller restart also failed to preserve active governance, entering observe mode with emergency stop enabled; a forced crash correctly entered the same safe state. Both applications' final health and VM cleanup were verified, but these unresolved performance and lifecycle results prevent a readiness claim. The 1.9.23 account-detection changes do not claim to fix either failure.

The subsequent 1.9.23 shutdown correction reproduces a clean-stop failure in the original packaged runtime with a 4.5-second loopback probe. The former three-second background join could expire before the probe finished, retaining the crash marker. Shutdown now shares a 20-second drain deadline across tracked HTTP requests, maintenance, and relay probes. Queued probes check the stop event before opening a connection, and cancelled batches are discarded. In-flight probes remain owned until their work completes. This deadline bounds the drain wait; it does not guarantee total process-exit time if an operating-system or database operation stalls.

SIGTERM/SIGINT handlers stay installed through cleanup so repeated stop requests do not interrupt the clean-session write. The original forced-kill and uncertain-governance safeguards remain in effect. The controller logs outstanding workers and request counts when draining fails. These changes passed the packaged local clean-restart and forced-crash checks; the corresponding Azure retest remains outstanding.

Run the lifecycle check with `python tools/smoke_release.py dist/sentinel-blue-1.9.23.pyz --exercise-lifecycle` on POSIX. It uses temporary credentials, a disposable local controller database, an enrolled local agent, and a delayed loopback HTTP endpoint. It validates the exact package checksum, signed operator transitions, unchanged governance after SIGTERM, safe governance after SIGKILL, and authenticated recovery backup. It does not stop host services or access the practice VMs.

Shutdown follows Python's documented [server shutdown thread requirement](https://docs.python.org/3/library/socketserver.html#socketserver.BaseServer.shutdown) and [thread join semantics](https://docs.python.org/3/library/threading.html#threading.Thread.join). Native Windows performance and competition readiness require separate evidence.
